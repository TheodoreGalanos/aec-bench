## 2. Ruling

### 2.1 `B4-D16` promotion contents

`B4-D16` is **accepted, minimum and field-allowlisted**.

One B5 promotion may contain exactly:

1. one public profile declaration;
2. one exact host-private physical member selected for the first runtime;
3. one host-private compact physical reference-check set; and
4. one public promotion manifest that inventories and traces the three payload
   files.

The promotion contains no family search results, rejected members, complete
engine trajectories, raw solver artifacts, generator/certifier code, study
history, task gold, institutional semantics, action policy, or mutable
workspace path.

Passing W4 is necessary but cannot promote anything. B5 may issue the manifest
only after one exact world generation passes replay, independent certification,
the complete W4 matrix, AG-01 through AG-13, rights review, visibility review,
package conformance, and physical research-absence checks.

### 2.2 `B4-D17` retirement point

`B4-D17` is **accepted, delayed and evidence-gated**.

No B3, B4, or B5 research implementation or authority is removed in W5 or B5.
Removal from the current repository tree requires:

1. one exact B5 V3 promotion manifest and package;
2. ASW-2A0's independently implemented strict asset-local reader;
3. successful package load and compact reference-check replay with
   `research/`, source documents, B3/B5 code, SWMM, build trees, and raw run
   artifacts physically absent;
4. a compact retained audit record binding the removed content by Git and
   SHA-256 identity; and
5. a dedicated retirement PR with its own absence and historical-recovery
   review.

Git history remains the historical recovery mechanism. A successful promotion
does not erase failed generations or their audit identities, and deletion from
the current tree does not make a discarded artifact authoritative.

### 2.3 Maturity consequence

W5 defines how B5 can issue an exact V3 package. It does not issue one.

The terms `promotion-manifest`, `package`, `receipt`, and `reference-check`
below are conceptual B4 specifications. They are not Python names, Pydantic
models, persisted platform contracts, public registry identifiers, CLI
surfaces, or compatibility promises. B5 will implement research-local
serializations. ASW-2A0 must later re-express the accepted semantics in the
owning asset-local package without importing W5 Markdown or B5 code.

## 5. Canonical byte profile

### 5.1 Reuse without code sharing

B5 receipts, declarations, payloads, inventories, and manifests use W2's
canonical JSON byte profile:

- UTF-8 without BOM;
- lexicographically ordered object keys by Unicode code point;
- exact fixed array order;
- no insignificant whitespace;
- one terminal LF;
- no duplicate, unknown, or omitted required key;
- physical scalars as canonical SI decimal strings;
- integers as JSON integers;
- booleans as JSON booleans;
- no null, exponent, leading plus, leading zero, decimal comma, `NaN`,
  infinity, or negative zero; and
- lower-case hexadecimal SHA-256 identities.

This is specification reuse, not implementation reuse. The generator,
certifier, W4 composer, promotion authority, package conformance checker, and
later ASW-2A0 reader must not obtain canonical bytes from one shared
claim-critical helper. Each named boundary reconstructs and compares bytes
with its own implementation.

### 5.2 Canonical path rules

Canonical content may contain only safe POSIX relative paths:

```text
segment = [a-z0-9][a-z0-9._-]*
path = segment ("/" segment)*
```

Paths containing an empty segment, `.` or `..` segment, leading slash,
backslash, colon, NUL, control character, percent-encoded traversal,
Unicode lookalike, symlink, device, socket, or FIFO reject.

The package root's absolute location is never canonical. Relocating an exact
package root changes no content identity. Relative payload paths are manifest
content because the strict reader must reject misplaced or extra files.

### 5.3 No canonical wall-clock or environment path

Canonical bytes exclude:

- generation or review timestamp;
- host, user, process, container, or workspace name;
- absolute source, build, install, run, log, report, or cache path;
- environment-variable name or value;
- Git working-tree location; and
- mutable branch, tag, latest, current, or accepted alias.

An operational log may record such observations outside the canonical receipt.
It never changes a receipt, generation, package, or manifest identity.

## 6. Content identities and non-circular hashing

### 6.1 Payload identity

For each payload:

```text
payload_content_id =
    sha256(
        "asw-0b5.promoted-payload.v1\0"
        || semantic_role
        || "\0"
        || canonical_payload_bytes
    )
```

`semantic_role` is one of the three roles in section 11. A supplied ID must
equal the recomputed value.

### 6.2 Package identity

The package inventory contains exactly one row per payload, ordered by exact
relative path. Each row contains:

```text
relative_path
semantic_role
payload_content_id
sha256
size_bytes
media_type
schema_identity
visibility_class
```

The package identity is:

```text
package_content_id =
    sha256(
        "asw-0b5.promoted-package.v1\0"
        || canonical_payload_inventory_bytes
    )
```

The manifest is not a payload row and therefore does not hash itself.

### 6.3 Manifest identity

The canonical manifest contains `package_content_id` and the exact inventory
but does not contain its own ID:

```text
promotion_manifest_id =
    sha256(
        "asw-0b5.promotion-manifest.v1\0"
        || canonical_manifest_bytes
    )
```

The promotion decision receipt binds the recomputed manifest ID. An external
caller or later reader may carry that ID, but adding it inside the same
manifest is forbidden self-reference.

### 6.4 World-generation identity

B5 constructs a canonical generation declaration that binds:

- profile and W1–W5 authority identities;
- exact member and W2 case identities;
- W4 probe catalogue identity;
- generator source, dependency, engine, and configuration identities;
- certifier source, dependency, and environment identities;
- exact replay ordinal policy;
- exact receipt-kind profile; and
- package/manifest specification identities.

```text
reference_world_generation_id =
    sha256(
        "asw-0b5.world-generation.v1\0"
        || canonical_generation_declaration_bytes
    )
```

The ID names one attempted generation design, not a successful result.
Changing code, dependencies, member, case set, engine build, certifier,
tolerance protocol, or receipt profile creates a different generation ID.

### 7.1 Receipt kinds

B5 emits exactly these canonical research receipt kinds:

| Ordered kind | Producer | Required parent identities | Terminal purpose |
| --- | --- | --- | --- |
| `generation-declaration` | B5 controller before execution | W1–W5 authorities, source/dependency identities | Freeze one attempt |
| `engine-build` | B5 generator build boundary | generation declaration, B3/W2 engine identities | Bind real pinned engine artifacts |
| `generator-case` | W2 generator | generation declaration, engine build, member, case, replay | Preserve one generation result or failure |
| `certifier-case` | W3 certifier | generation declaration and exact candidate byte identities | Preserve independent result or failure |
| `w4-case` | W4 composer | certifier result and W4 identity | Preserve composed numerical/qualitative result |
| `sensitivity-member` | W4 sensitivity runner | generation declaration, probe, mapped case results | Preserve one OAT/INT/BND/ENG outcome |
| `family-decision` | B5 family aggregator | all required case, mutation, probe, and replay results | Freeze family acceptance/rejection |
| `gate-decision` | B5 gate reviewer | family decision and AG evidence inventory | Record AG-01 through AG-13 individually |
| `rights-review` | B5 promotion review | exact proposed file/field inventory and B2/W1 mappings | Reject unlawful or unmapped content |
| `visibility-review` | B5 promotion review | exact proposed file/field inventory | Reject leakage or unowned visibility |
| `package-conformance` | Separate B5 package checker | exact manifest and payload bytes | Reject shape, hash, version, or allowlist drift |
| `absence-proof` | Separate B5 package-only environment | exact manifest and payload bytes | Prove research/tool absence and compact replay |
| `promotion-decision` | B5 promotion authority | all prior pass identities | Issue or refuse one manifest |

No kind is optional when its stage applies. Failed or rejected receipts remain
part of the research graph and are never overwritten by a later attempt.

### 7.2 Common receipt envelope

Every receipt contains:

- exact receipt kind and version;
- exact profile and generation identity;
- exact authority identities applicable to that kind;
- exact ordered parent receipt identities;
- exact input content identities;
- deterministic terminal state and first failure;
- exact output content identities that were actually produced;
- visibility class;
- explicit `promotable=false`, except that a successful
  `promotion-decision` may name one manifest and package as promoted; and
- no path, timestamp, hostname, or mutable alias.

Kind-specific bodies retain all terms required by W2–W4. A common envelope does
not flatten residuals, failure precedence, warning details, rejected probes,
or independent-environment evidence.

### 7.3 Receipt identity

```text
research_receipt_id =
    sha256(
        "asw-0b5.research-receipt.v1\0"
        || receipt_kind
        || "\0"
        || canonical_receipt_bytes
    )
```

Parent arrays form a directed acyclic graph. Missing, duplicate, cyclic,
unknown-kind, wrong-generation, or wrong-profile parent references reject.
A graph is complete only when every root terminates at the exact
`generation-declaration` and every expected leaf is present.

### 7.4 Failures are retained

Rejection receipts record:

- the first failure under the owning protocol's precedence;
- every check completed before it;
- the failed member/case/probe/mutation identity;
- relevant raw residual or classification evidence;
- the immutable input identities; and
- the owning repair route.

They do not include a replacement value, tuned threshold, or successful
sibling as if it repaired the failed attempt.

## 8. Provenance link model

### 8.1 Stable link identities

Every promoted field has exactly one stable `field_semantic_id` and at least
one link from each applicable register:

| Register | Required link |
| --- | --- |
| Evidence | B2 claim/evidence ID and evidence class |
| Source | B2 source ID with citation or accepted hash |
| Rights | Exact rights class and disposition ID |
| Assumption | W1 assumption/parameter identity or explicit `none` |
| Unit | Quantity identity, canonical SI unit, and conversion identity |
| Transformation | W1/W2 equation or exact original transformation identity |
| Generation | Member, case, semantic candidate field, and receipt identities |
| Certification | W3 residual/invariant/reference/mutation identities |
| Sensitivity | W4 probe and ordering identities |
| Claim | Permitted claim and prohibited-claim identities |
| Visibility | Exact W5 visibility class and later projection owner |

`none` is allowed only when the register is genuinely inapplicable and the
reason is explicit. Missing is not equivalent to `none`.

### 8.2 Field addressing

Fields are addressed by:

```text
(semantic_role, RFC-6901 JSON Pointer)
```

The pointer addresses a leaf scalar or an entire fixed-shape object whose
children have the same authority, rights, unit treatment, and visibility.
Wildcards, array globs, prefix permission, regular expressions, and
“all current/future fields” are forbidden.

### 8.3 Derivation chain

Every promoted numerical field must trace:

```text
source or declared S-class assumption
  -> exact W1 parameter/equation
  -> exact W2 rendering or semantic transformation, if applicable
  -> exact generated value and representation
  -> W3 independent check
  -> W4 tolerance/sensitivity result
  -> B5 accepted field
```

The manifest may compress repeated link sets by exact content-addressed
reference, but it may not omit a link because another field looks similar.
A citation cannot replace a transformation, and a generator hash cannot
replace independent certification.

### 8.4 Source metadata versus source bytes

For `Cite-only` sources, the manifest may carry only allowlisted citation
metadata already present in B2:

- stable B2 source ID;
- title;
- publisher or author;
- public URL or bibliographic identifier;
- evidence class;
- rights class; and
- concise repository-authored claim mapping.

It may not carry quoted passages, tables, images, documents, scraped bytes,
page caches, embeddings, or reconstructed source data. Citation metadata
does not make the promoted physical value source-derived; original S-class
values retain their synthetic assumption identity.

## 9. Visibility classes

Every file and field receives exactly one class:

| Class | Meaning | Promotion treatment |
| --- | --- | --- |
| `public` | Safe for repository/public audit; contains no latent episode truth, task answer, private case, or future event | Allowed only in the public profile or manifest roles |
| `actor-visible` | Eligible for a later ASW-2A3 actor projection after information-set binding | No static W5 payload uses this class; presence in a package never exposes it automatically |
| `host-private` | Runtime or package-reader input unavailable to the agent | Allowed only in exact physical-member and compact-reference roles |
| `certification-private` | Residual details, mutations, full references, family search, and rejection evidence used only for certification | Research receipt graph only; forbidden from promoted payloads |
| `holdout-sensitive` | Sealed cases, future events, evaluator targets, or any material whose disclosure could contaminate evaluation | Forbidden from the first promoted package and public manifest |

Visibility is not inferred from directory, filename, Git status, hash, or
rights. A public right does not imply public benchmark visibility. A
host-private file is not actor-visible because the actor can theoretically
read JSON; the runtime must not mount or project it.

Mixed-visibility payload files are forbidden in the first package. The public
manifest may reference host-private payload identities, roles, hashes, sizes,
schema identities, rights decisions, and provenance summaries, but not their
latent numerical contents.

## 11. Exact promoted payload roles

### 11.1 `public-profile`

This role contains only:

- profile identity and schema identity;
- fictional Lower Hunter context;
- one asset and exactly Pump A/Pump B component identities;
- initial A-duty/B-standby topology and one-transfer maximum;
- synthetic V3 claim ceiling;
- permitted and prohibited claim IDs;
- exact generation identity and manifest-specification identity;
- exact repository licence identifier, required redistribution notice, and
  allowlisted attribution metadata; and
- no numerical latent state, physical member value, scenario, actor,
  authority, obligation, or score.

The profile payload contains no concrete package or promotion-manifest ID.
Either would create a circular hash because the manifest inventories this
payload.

### 11.2 `physical-member`

This host-private role contains only the exact selected runtime member:

- profile, member, and schema identities;
- exact asset/component/topology declarations;
- exact canonical SI parameter values and units accepted under W1;
- clean pump, wet-well, system, inflow, mechanism, progression, capability,
  observation, intervention, transfer, and resource rule identities and
  parameters;
- exact fixed composite values and ordering rules needed by ASW-2A1;
- no generated engine series;
- no executable expression, script, plugin, import path, or solver call; and
- no scenario timing, action authority, obligation, institutional record,
  evaluation, or agent-visible projection.

The payload is data for one exact member. It does not ask ASW-2A1 to interpret
W1 Markdown or arbitrary formula strings.

### 11.3 `physical-reference-checks`

This host-private role contains only compact, non-study physical checks:

- profile, member, generation, and schema identities;
- exact input-state identities;
- exact rule or transition identity;
- finite expected scalar, interval, classification, or content-hash result;
- canonical units and representations;
- exact W3 check and W4 tolerance identities;
- enough clean, degraded, intervention, transfer, ambiguity, no-maintenance,
  zero-flow, boundary, and label-symmetry checkpoints to falsify a wrong
  ASW-2A0/ASW-2A1 reader or kernel; and
- no complete trajectory, actor action, best response, score, study history,
  future event schedule, mutation answer key, or sealed case.

The reference checks are not a second physics implementation. ASW-2A0 verifies
package integrity and exact compact references. ASW-2A1 later implements the
physical semantics and proves the same references independently.

### 11.4 Manifest

The manifest is a public audit envelope. It inventories the three payloads and
their fields but contains none of the host-private field values.

The package root contains exactly:

```text
promotion-manifest.json
<one public-profile payload>
<one physical-member payload>
<one physical-reference-checks payload>
```

B5 freezes the three exact relative payload paths in one issued manifest.
`promotion-manifest.json` is exact only inside the B5 research package.
W5 does not make the illustrative payload role names or B5 package layout into
production filenames; ASW-2A0 must establish its owned asset-local layout.

Every payload leaf is owned by exactly one field row. Every field row resolves
to exactly one payload leaf or fixed-shape same-authority object. Extra,
missing, overlapping, wildcard, or dangling rows reject.

### 12.4 Compatibility and supersession

The first package declares:

- exact package and payload schema identities;
- strict unknown-file and unknown-field rejection;
- no compatible predecessor package;
- no migration;
- replacement only by a new manifest and package content ID;
- historical package bytes remain immutable; and
- mutable `latest` or in-place replacement is forbidden.

ASW-2A0 may later define an asset-local reader for only this exact version. It
does not promise that future package versions will load.

## 14. Promotion decision algorithm

The promotion authority executes these stages in order:

1. verify exact W1–W5 authority identities;
2. verify generation declaration and complete acyclic receipt graph;
3. require real engine build and every mapped W2 run/replay result;
4. require separately executed W3 certification and environment-absence
   receipts;
5. require every W4 case, mutation, sensitivity, ordering, and family result;
6. require `family-w4-checks-pass`;
7. require AG-01 through AG-13 each exactly `pass`;
8. require V0, V1, and V2 evidence each exactly `pass`;
9. construct the exact three-payload proposal from allowlisted fields only;
10. run rights review and visibility review independently over every file and
    field;
11. construct payload bytes, inventory, package ID, and manifest bytes;
12. run the separate package conformance checker;
13. run the physical research/tool absence proof and compact reference replay;
14. rerun package construction in a second fresh workspace and require exact
    package/manifest semantic equality;
15. require prohibited claims and V4-unclaimed status;
16. issue one immutable promotion decision binding manifest and package IDs; and
17. never modify the issued bytes.

An earlier failure stops later execution. The authority does not partially
promote passing files from a failed package.

## 15. Promotion result states

| Ordered state | Meaning |
| --- | --- |
| `promotion-input-reject` | Authority, generation, receipt graph, or required bytes are missing or contradictory |
| `promotion-generation-reject` | A W2/W3/W4 case, replay, mutation, probe, ordering, or family result rejects |
| `promotion-pending-demonstration` | An AG or V0–V2 criterion is not yet demonstrated |
| `promotion-gate-reject` | An AG criterion fails |
| `promotion-rights-reject` | A source, rights, derivation, attribution, or redistribution rule fails |
| `promotion-visibility-reject` | File/field classification is missing, mixed, contradictory, or leaks prohibited material |
| `promotion-manifest-reject` | Canonical bytes, shape, field allowlist, inventory, hash, version, or package replay fails |
| `promotion-absence-reject` | The package needs a research path, source, engine, generator, certifier, network, or undeclared file |
| `promotion-v3-issued` | All prior stages pass and one exact manifest/package pair is issued |
| `promotion-internal-error` | The promotion path cannot complete its own deterministic calculation |

Precedence is table order except that an internal error remains an internal
error. Only `promotion-v3-issued` may carry `promotable=true`, and then only for
the exact manifest/package pair. It does not promote the receipt graph,
research code, sibling members, or source material.

| Any AG `fail` | `promotion-gate-reject` |
| `Cite-only`/`Excluded` source bytes or unclassified rights | `promotion-rights-reject` |

## 17. Package conformance and absence proof

### 17.1 Separate package checker

B5 implements a package conformance checker that imports neither the generator
nor the independent certifier. It:

- canonicalizes manifest and payload bytes independently;
- recomputes every file, payload, package, and manifest identity;
- enforces exact root inventory and field ownership;
- enforces path, file-type, rights, visibility, version, and claim rules;
- verifies receipt references are well-formed and cross-consistent without
  dereferencing or importing receipt-producing code;
- executes only compact physical reference-check comparisons; and
- cannot issue the promotion decision it checks.

The checker is research-local and non-production. ASW-2A0 later implements its
own strict reader rather than importing this checker.

### 17.2 Physical absence environment

The absence proof begins from a new root containing only:

- the exact manifest;
- the three exact payloads; and
- the independently installed package conformance entrypoint needed for the
  B5 check.

The environment physically lacks or makes unreadable:

- the repository `research/` tree;
- B1–W5 Markdown;
- source documents and intake attachments;
- external prototype files;
- B3 spike source and fixtures;
- B5 generator/controller code;
- B5 independent-certifier code;
- SWMM source, executable, libraries, input, output, and report files;
- prior run roots, logs, caches, and receipts other than content identities
  represented in the manifest; and
- network access.

The check fails on fallback lookup, undeclared default, path probing, network
attempt, or missing-field substitution.

### 17.3 Compact reference replay

The package-only checker validates:

- public/profile/member identity cross-links;
- parameter unit and exact-value shape;
- package field completeness;
- precomputed compact reference identities and expected intervals;
- label symmetry and one-transfer topology declarations;
- nonclaim and visibility declarations; and
- exact second-workspace package equality.

It does not rerun SWMM, reproduce W3 equations, or claim independent physical
certification. Those are B5 research evidence bound by receipt identity.
ASW-2A1 later proves the implemented physical kernel against the compact
references.

### 17.4 String and dependency scan

Before promotion, B5 scans canonical payload bytes and package-reader dependency
metadata for:

- absolute paths and known research-root fragments;
- source/prototype filenames;
- SWMM executable/library/input/output/report names;
- generator/certifier Python module names;
- mutable aliases;
- actor, authority, obligation, score, answer, future-event, and holdout
  fields; and
- unknown media types or executable content.

A clean scan is necessary but not sufficient; structural checks still run.

## 18. Rights and claim review

The B5 rights reviewer must prove:

1. every promoted byte is repository-authored original material or exact
   allowlisted redistributable metadata;
2. no `Cite-only` source content appears beyond section 8.4 metadata;
3. no `Excluded` byte or derived prototype structure appears;
4. every numerical value is identified as original S-class or a certified
   derivation from accepted inputs;
5. every transformation and unit conversion is explicit;
6. every required attribution is present;
7. no rights class is inferred from a file extension or software licence;
8. public-domain SWMM status does not promote SWMM artifacts;
9. V4 is exactly `unclaimed`; and
10. all prohibited claims remain machine-visible in the public profile and
    manifest.

The review records one decision per file and field. “Repository-authored” is
not a substitute for evidence, rights, or claim review.

## 19. Retirement and current-tree policy

### 19.1 Until B5 promotion

Retain:

- B1/B2/B3/B4 authority documents;
- B3 compact verification;
- tracked B3 executable spike evidence;
- B5 research implementation and tests; and
- all canonical generation/rejection/promotion receipts required for review.

Raw local builds and engine run roots remain ignored and disposable after their
content identities and required evidence are safely recorded.

### 19.2 After B5, before ASW-2A0

Retain the same current-tree evidence. A B5 manifest is not proof that a
production reader can load it. No research subtree is removed merely to make
an absence test easier.

### 19.3 After ASW-2A0

A dedicated retirement review may remove from the current tree:

- B3 executable source, tests, fixtures, patch, and exact `.gitignore`
  exceptions;
- B5 generator, certifier, sensitivity, package-checker source and tests after
  their required historical identities are captured; and
- detailed B4 protocol documents when a compact retained B4 decision record
  and B5 promotion summary bind every removed content hash.

The review must retain or re-express:

- B1 claim/nonclaim authority;
- B2 evidence/rights/derivation summary;
- B3 engine-role decision and compact verification;
- W6 final B4 decision and complete authority hash chain;
- B5 promotion decision summary;
- the exact promoted manifest/package in the owning asset-local location; and
- Git commit identities needed to recover removed research.

Removal occurs only if ASW-2A0 and its tests succeed with the candidate
research files absent before deletion. The retirement PR repeats that evidence
after deletion.

### 19.4 Rollback

If a promoted package or ASW-2A0 reader is invalidated:

- mark the exact manifest/package superseded or revoked without overwriting it;
- stop dependent ASW-2 work;
- recover historical research by its recorded Git identity if needed;
- issue a new B5 generation and manifest after repair; and
- never retarget a mutable alias to conceal the invalidation.
