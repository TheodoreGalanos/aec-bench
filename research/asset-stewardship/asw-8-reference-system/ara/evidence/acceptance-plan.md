# ASW-8 acceptance plan

The authoritative detailed matrix is section 16 of
`research/asset-stewardship/asw-8-reference-system-design.md`.

## Provider-free evidence

Use focused unit cases for strict v2 identity, topology, running-set and start
rules, the four pump-boundary modes, separate functional-check test exposure,
failed-check retention, assured capacity, visible-schedule outage admission,
strict legacy-or-pool resource routing, pool arithmetic, priority,
exactly-once generation, target assessment, failed verification, and all four
balance equations.

Require the separate host-only Operations boundary-review receipt after
accepted verification and C's no-finding inspection. Missing or invalid review
input must leave the current boundary and assurance unchanged.

Use focused integration cases for shared exclusion, availability windows,
suspension, resume, cancellation, common hard stops, baseline cover
attribution, all work-generation rules, snapshot, handover, crash recovery,
v4 replay, and ASW-7 branch isolation. Include child temporal-corpus
initialisation with no parent-private retrieval records, the accepted same-time
event order, W3 completion at 14:00 before its 15:00 closure, and calendar
versus per-pump runtime boundaries across service-running and test-running
pumps.

Use the real temporal repository and gateway at Day 1 02:00 and 04:00. The C
collateral-note search must change from absent to one fetchable result in the
direct root, Harbor root, and an isolated child. Bind the branch-neutral RS1
template in the descriptor and each realised root corpus in its own manifest.
The child must inherit the parent's exact public bundle, add its own ancestry,
and start fresh private retrieval state. Keep the current v1 builder unchanged.

Use focused end-to-end cases for the complete Day 0 to Day 2 reference journey,
installed JSON, direct verification and evaluation, local Harbor, strict
TrialRecord import, rollout-control v2 routing, normalized semantic parity, and
historical byte compatibility. Do not compare the full `EvaluationResult`
across direct and Harbor runs because its evidence identities are intentionally
transport-specific.

The journey uses immediate persistent duty assignments. Only
`continue_operation` advances time. Pump C is the normal baseline before the
peak, C replaces B during the peak, and Pump A is the normal baseline after the
peak.

Do not run the full repository suite after each implementation step.

## Agent evidence

After the provider-free gate passes, one separately bounded real-agent journey
can use the same actor projection and closed tools. Natural-language reasons
are valid. Typed action codes and IDs remain mandatory where the process needs
them.

The agent journey checks behaviour and usability. It does not prove physical,
persistence, replay, privacy, or conservation semantics. It is not a provider
study and it does not authorise repeated runs.
