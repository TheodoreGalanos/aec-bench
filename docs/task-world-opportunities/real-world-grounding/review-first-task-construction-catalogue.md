# Review-First Task Construction Catalogue

This catalogue extends the SSC-01 review-first pattern to the other SSC notes at the conceptual construction layer. It is for SME review before implementation. It does not add runtime templates, tests, model runs, source-pack hardening, accepted project evidence, generated benchmark readiness, or benchmark readiness.

The intent is to preserve every existing formula/synthetic package as a useful baseline, then design additive issue-review companions that ask a reviewer to decide whether a source packet is ready to issue.

## Construction Rules

Use the SSC-01 cleanup standard without dilution:

- Keep existing formula templates and all-product synthetic examples as saved artifacts.
- Make the review task file-backed: document register, domain source files, criteria/comments, comment/action register, and claim-boundary note.
- Use the same status vocabulary: `pass`, `fail`, `not_applicable`, `insufficient_data`.
- Keep instructions and system prompts variant-blind. They may describe the generic review protocol and schema, but they may not map a hidden defect to its item, status, omitted key, citation, or readiness decision.
- Put methods, code editions, software-export conventions, unit conversions, and authority criteria in source files, not prompt scaffolding.
- Treat sub-1.0 model behavior after SME review as potential evidence, not automatically as something to tune away.

## Universal Review Matrix

Every task should specialize the same nine review rows:

| Item | Generic role |
| --- | --- |
| `RLR-01` | Packet completeness: required files, IDs, revisions, and registers are present. |
| `RLR-02` | Object identity: asset IDs, location frames, cases, scenarios, and source revisions reconcile. |
| `RLR-03` | Primary basis: the controlling calculation/model/report basis is traceable, current, and recomputable from the source packet. |
| `RLR-04` | Primary adequacy: the exposed asset clears the source-owned criterion, or the task reports `insufficient_data` when the controlling input is missing. |
| `RLR-05` | Scenario consequence: the same operating, hazard, event, load, or construction case is used across affected disciplines. |
| `RLR-06` | Secondary-discipline resilience: adjacent capacity, power, controls, access, constructability, or operations checks are source-backed. |
| `RLR-07` | Comment/action closure: critical comments are closed or have blockers; carried minor actions have owner, due date, and scope. |
| `RLR-08` | Readiness consistency: the final issue decision follows the matrix, findings, requests, and action register. |
| `RLR-09` | Claim boundary: the response does not overclaim approval, standards compliance, accepted evidence, source-pack hardening, or benchmark readiness. |

## Product-Family Expansion Rule

After SME review of an anchor, expand the same review-first shape across that SSC's eight product families. The expansion should follow this rule:

1. Preserve the existing runnable/formula template named in `product-expansion-catalogue.md`.
2. Name the additive review task as `Review the <product> package for issue`.
3. Use a source packet with a document register, product-specific source files, criteria/comments, and comment/action ledger.
4. Pick exactly one first genuine-failure route for `RLR-04`.
5. Keep the universal hidden variants: missing critical evidence, stale basis revision, identity mismatch, scenario copy-forward, open critical comment, minor carried comment, and genuine criterion failure.
6. Add a source-policy or authority-boundary variant only when the product is naturally about evidence provenance or approval boundaries.
7. Do not implement templates, run tests, or run models until SME review approves the source packet and review matrix, and not before post-cleanup SSC-01 model probes exist under the variant-blind prompts.
8. When two SSC sections reference the same physical product (for example the BESS hazard, marine fender, dewatering, or blower-acoustic rows), implement exactly one template. Ownership follows the review judgment, not the equipment: hazard classification lives with `SSC-19`, ground models with `SSC-07`, certificates with `SSC-15`, structures with `SSC-14`. The other section keeps its row as a cross-reference to the owning template.
9. Treat the construction maps below as a menu, not a queue. The implementation dispositions section records which rows are worth building; do not implement cut rows without a new justification.

## SME Review Checklist

Ask SMEs to check:

- Is the source packet something a practitioner would actually receive or assemble?
- Is `RLR-04` the right controlling adequacy check, or should the task measure a different review decision?
- Which missing input should be `insufficient_data` rather than `fail`?
- Which source identity drift is most realistic: asset ID, chainage/station, datum, operating case, design storm, load combination, code edition, or equipment tag?
- Are the source-owned conventions sufficient without telling the model the hidden defect's answer?
- Is the first genuine failure too arithmetic-heavy, or does it force source inventory, handoff discipline, and readiness judgment?
